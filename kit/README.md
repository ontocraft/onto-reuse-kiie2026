# 제조 AI 시작 키트

CMM 측정 파일(QIF)과 CSV 세 개를 넣으면, 공개 온톨로지(IOF) 어휘로 지식그래프를 만들고
「부적합이 난 부품을 어느 설비에서 만들었고 그때 설비 정비 상태가 어땠나」 같은 질문에
답한다. 처음부터 스키마를 설계하지 않고 시작하려는 것이 목적이다.

    python scripts/mfg_kit.py                        # 예제로 실행
    python scripts/mfg_kit.py --data 내자료 --qif a.qif b.qif
    python scripts/mfg_kit.py --data 내자료 --qif     # QIF 없이 measurements.csv 로

## 넣는 것

틀은 `templates/` 에 있다. 열 이름을 바꾸지 않는다.

| 파일 | 어디서 | 열 |
|---|---|---|
| QIF 측정 파일 | CMM 소프트웨어 | 그대로. `Part/ModelNumber` 와 `ActualComponent/SerialNumber` 를 쓴다 |
| `measurements.csv` (QIF 가 없을 때) | CMM·검사 기록 내보내기 | 품번 · 일련번호 · 특성 · 값 · 판정(PASS · FAIL · UNDEFINED). 한 줄이 측정 하나 |
| `mes_process_runs.csv` | MES | 품번 · 일련번호 · 실행 번호 · 공정 · 설비 문자열 · 작업자 · 시작 · 끝 |
| `equipment_registry.csv` | 설비 대장 | 설비 ID · 그 설비를 부르는 문자열 · 어느 시스템의 문자열인가 · 종류 · 역할 |
| `maintenance_states.csv` | CMMS | 설비 문자열 · 상태(Operating · Degraded · Failed) · 시작 · 끝 · 작업지시 |
| `machine_events.csv` (선택) | MTConnect 등 기계 로그 | 설비 문자열 · 사건 이름 · 시작 · 끝 · 그 사건이 속한 공정 실행 번호 |
| `part_registry.csv` (선택) | 품질 · 생산 | 같은 부품을 시스템마다 다르게 부를 때, 부품 ID · 문자열 · 시스템 |

QIF 를 내보내지 못하는 CMM 이 더 많다. 그럴 때는 검사 기록을 `measurements.csv` 틀로 내보낸다.
키트가 QIF 에서 쓰는 것은 판정과 부품 식별뿐이라 CSV 로도 같은 질문에 답한다.
`examples-csv/` 는 공개 표본 하나의 측정 600 건을 이 틀로 옮긴 예제다.

기계 사건은 **설비 상태가 아니다.** 정비 기록이 없을 때 「이 부품을 가공하는 중에 중단이
있었는가」까지만 답한다. NIST 자료에서는 PROGRAM_STOPPED 가 기계가 아니라 그 부품 프로그램의
상태라서, 시간이 겹치는 것으로 설비 상태를 추정하면 다른 부품의 중단까지 끌려온다. 그래서
사건은 `run_id` 로 그 작업 실행에 묶고, 묶인 것만 질의한다.

설비 대장에는 **같은 설비를 시스템마다 다르게 부르는 문자열을 모두** 한 줄씩 적는다.
예제에서 MES 는 `M-07`, CMMS 는 `MC007` 로 같은 설비를 부른다.

## 키트가 메우는 끊긴 곳 넷

공개 자료를 그대로 쓰면 아래 넷에서 질문이 끊긴다. 결정기록에 근거가 있다.

| 끊긴 곳 | 키트의 처방 | 결정기록 |
|---|---|---|
| QIF 의 공정 참조(`ManufacturingProcessId`)가 비어 있다. 공개 QIF 62 개 모두 0 | 측정 → 실물 부품 → **품번/일련번호** → MES 공정 실행 | 0035 |
| 설비가 시스템마다 다른 문자열이다 | IOF `Identifier` 가 `designates` 로 설비 하나를 지칭 | 0036 |
| 「정비 대상」으로 물으면 0 건이다(역할로 정의된 클래스) | 적재할 때 IOF 의 역할 정의에서 규칙을 뽑아 분류를 구체화 | 0037 |
| 「그때」의 정비 상태를 물을 수 없다 | IOF 정의대로 정비 상태를 시간 구간으로 두고, 공정 시각이 구간 안에 드는지로 묻는다 | 0038 |

## 예제로 돌린 결과 (2026-10-12)

QIF 는 공개 표본 두 개(000454 · 000473)다. **MES · 설비 대장 · CMMS 는 지어낸 시험
데이터다.** 답의 개수에는 의미가 없고, 끝까지 이어지는지를 본다.

| 단계 | X1 에서 살아남은 부적합 측정 |
|---|---:|
| 부적합 측정 | 224 |
| → 부품(품번/일련번호) | 224 |
| → 공정 실행 | 224 |
| → 설비 | 224 |
| → 그때의 정비 상태 | 224 |

- 역할 분류를 구체화하기 전에는 X1 이 0 건이고 후에는 224 건이다
- P2(공정의 설비와 작업자), X2(정비 상태별 부적합)는 **어휘를 더하지 않고 질의만 써서** 답했다
- 그래프가 쓴 어휘는 IOF 18 · BFO 1 · QIF 요소 이름 3 · 키트 4 다. 키트가 만든 넷은
  식별자 값·체계와 시작·끝 시각이다. IOF 에 그 자리를 채울 속성이 없었다(0036, 0038)

## 현장 열 이름을 틀에 맞춘다

MES · CMMS 내보내기의 열 이름은 회사마다 다르다. 자주 보는 이름을 틀의 열로 바꾸는 예다.
값은 바꾸지 않고 열 이름만 바꾼다.

| 틀의 열 | 현장에서 흔한 이름 |
|---|---|
| `model_number` | 품번 · 품목코드 · 도번 · PART_NO · ITEM_CD |
| `serial_number` | 일련번호 · 시리얼 · S/N · LOT_SEQ(로트 안 순번이면 품번·로트와 함께) |
| `run_id` | 작업번호 · 실적번호 · WORK_ORDER_NO + 공정순번 |
| `operation` | 공정 · 공정코드 · OP_CD |
| `machine_id` | 설비코드 · 호기 · MC_CD · EQP_ID |
| `operator_id` | 작업자 · 사번 · WORKER_ID |
| `start` / `end` | 시작일시 · 종료일시 · START_DT · END_DT (ISO 8601 `2026-09-01T08:00` 로 바꾼다) |
| `identifier` (설비 대장 · CMMS) | 설비코드 · 자산번호 · ASSET_NO. 시스템마다 다른 이름을 모두 한 줄씩 |
| `state` | 설비상태 · 가동/고장 구분. Operating · Degraded · Failed 셋으로 묶는다 |
| `work_order` | 정비 작업지시 · WO_NO |

시각은 시간대가 같아야 한다. MES 와 CMMS 의 시간대가 다르면 먼저 맞춘다.

## 적재하기 전에 점검한다

    python scripts/mfg_kit_check.py --data 내자료 --qif a.qif

자료만 읽고 아래를 판정한다. 끊기는 항목이 있으면 종료 코드 1 이다.

| 항목 | 걸리면 |
|---|---|
| MES 의 품번/일련번호가 품질 쪽 부품에 있는가 (부품 대장을 거친다) | 측정 → 공정이 끊긴다 |
| 같은 일련번호가 다른 품번에도 있는가 | 품번 없이 이으면 섞인다 |
| MES · CMMS · 기계 사건의 설비 문자열이 설비 대장에 있는가 | 공정 → 설비가 끊긴다 |
| 정비 상태에 시작 시각이 있고, 끝 없는 상태가 설비마다 하나뿐이고, 구간이 겹치지 않는가 | 「그때」를 물을 수 없거나 답이 둘 나온다 |
| 정비 상태 파일이 있는가 | X1 의 마지막 연결을 답할 수 없다 |

예제는 통과한다(일련번호가 두 품번에 겹치지만 품번과 함께 쓰므로 경고만). NIST 자료는
「정비 상태 파일 없음」에서 걸린다. 역할이 바뀌면 분류를 다시 적용하는 것은 자료로 판정할
수 없어 점검하지 않는다.

## 질문을 더하는 비용

키트가 자리를 잡은 뒤 질문 넷을 더 넣어 보았다(`scripts/mfg_kit_more.py`).
넷 다 어휘를 더하지 않았고 질의는 5 ~ 9 줄, 실행은 130 ms 안이다. 사람이 질의를 쓰는
시간은 재지 않았다.

| 질문 | 줄 | 실행 |
|---|---:|---:|
| Q1 측정값과 정의의 공차, 판정 | 6 | 122 ms |
| Q2 품번별로 부적합이 처음 난 공정 실행 시각과 그 뒤 건수 | 6 | 70 ms |
| M11 설비의 현재 정비 상태(끝 시각이 없는 상태) | 5 | 4 ms |
| X5 정비 작업지시가 다룬 구간에 만든 부품과 그중 부적합 | 9 | 36 ms |

Q1 은 측정 → 항목 → 명목 → 정의를 따라가 공차를 붙인다. 형상 공차(`ToleranceValue`, 값이
그 이하면 적합)에서는 판정과 값을 대조한다. 공개 표본에서 405 건 중 15 건(직각도 특성 하나)이
어긋났다. 측정 요소의 `MaxValue` · `MinValue` 는 공차가 아니라 측정값의 최대·최소다.

역량 질문 26 개의 현황은 `scripts/mfg_kit_status.py` 가 센다. 질의를 써서 답을 받은
것 6, 요소는 있고 자료가 없는 것 16, 요소가 부족한 것 4 다.

## 로트 단위 생산

일련번호가 없으면 `measurements.csv` 와 `mes_process_runs.csv` 에 `lot_number` 열을 두고
`serial_number` 를 비운다. 키트는 로트를 BFO 객체 집합체로, 식별자를 IOF `LotIdentifier` 로
둔다. 질문은 로트 단위로 답하고 로트 안의 개별 부품은 가리지 못한다.

## 규모

합성 자료로 재었다(`scripts/mfg_kit_scale.py`, 2026-10-12). 부품 수는 측정의 1/10,
설비 20 대, 설비마다 정비 상태 5 구간이다.

| 측정 | 트리플 | 적재 | 역할 분류 | X1 질의 |
|---:|---:|---:|---:|---:|
| 1,000 | 7,695 | 0.1 s | 0.0 s | 1.7 s |
| 10,000 | 67,095 | 0.5 s | 0.0 s | 185 s |

적재와 분류는 빠르지만 rdflib 메모리 그래프의 X1 질의는 10 배 자료에 100 배 느려진다.
속성 경로를 없앤 질의도 208 s 였다. **메모리 그래프는 시험용이다.** 측정이 수천 건을
넘으면 아래처럼 Neo4j 로 내보내 질의한다.

## Neo4j 로 내보낸다

    python scripts/mfg_kit_export.py --data 내자료 --qif a.qif   # out/kit-neo4j/
    neo4j-admin database import full --nodes=nodes.csv --relationships=rels.csv neo4j

라벨은 모두 `Kit` 접두어다(`KitPieceOfEquipment` 등). 운영 데이터베이스에 넣지 않고, 제약과
인덱스는 만들지 않는다. 예제는 노드 1,198 · 관계 2,235 다.

## 아직 못 하는 것

- 실제 MES · CMMS 자료로 돌려 보지 않았다. 일련번호 표기가 MES 와 QIF 에서 다르면 정규화가 필요하다
- 로트 단위는 로트까지만 잇고 로트 안의 개별 부품은 가리지 못한다
- QIF 문서에 `Part` 가 여럿인 조립품은 다루지 않는다
- 역할 규칙은 IOF 공통·정비 모듈의 13 개만 뽑는다. 다른 모듈은 읽지 않는다
